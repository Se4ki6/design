# 問題: 注文と売上速報の基盤（上級）

## 背景

EC サイトで、注文の確定処理と、運営向けの売上速報画面を設計する。注文確定後は発送処理とメール通知を行う。一方、利用者の閲覧・カート追加などの行動を大量に集め、売上速報と合わせて表示したい。決済事業者からは日次の精算 CSV が Blob Storage に届く。

## 前提と要件

- 注文 API は Azure App Service で動き、ピーク時に毎秒 100 件の注文がある
- 注文・明細・在庫の整合性が重要。注文が確定した事実を後続処理へ確実に伝える
- 発送依頼とメール通知は数分遅れてもよい。失敗時は個別に再試行できること
- 閲覧・カート操作などの行動イベントはピーク時に毎秒 20,000 件。直近 7 日分を再集計できること
- 売上速報画面は 1 分程度の遅れを許容する。古い集計値が一時的に表示されても、注文そのものは失われないこと
- 決済事業者が日次で置く精算 CSV と注文を照合し、差異を担当者が確認できること
- 候補として Azure SQL Database、Azure Cosmos DB、Blob Storage、Service Bus、Event Hubs、Event Grid、Azure Functions、Azure Container Apps を使える

## 設問

1. 注文確定、発送依頼・メール通知、行動イベント収集、精算 CSV 到着の4つに対して、Service Bus・Event Hubs・Event Grid のどれを使うか。メッセージの性質と再試行・再読込の要件から説明せよ。
2. 注文・在庫、売上速報、行動イベントの原本、精算 CSV と照合結果を、それぞれ RDB・NoSQL・Blob Storage のどこに置くか。各データの正本と、遅延を許容する参照用データを明示せよ。
3. Azure SQL への注文確定は成功したが、後続処理への通知に失敗した場合、発送依頼と売上速報の更新を失わない設計を示せ。重複通知を受けた Functions 側の対処も述べよ。
4. Event Hubs の行動イベントを Azure Container Apps 上の処理で集計する場合、重複・順序・処理停止・再読込をどう扱うか。速報値を後から再計算する方法も示せ。
5. 売上速報と注文 DB の数字が一時的に違う場合、画面と運用でどう扱うか。速報の更新遅延、未処理件数、照合差異をどう監視するか。
6. 精算 CSV の到着通知が重複した場合に、安全に照合を開始する条件を設計せよ。アップロード完了の判定と、完成した Blob の中身が欠けていた場合の扱いも述べよ。

## ヒント

- 注文の「必ず後続処理を行う」要求と、行動ログの「大量に集めて読み直す」要求は異なる
- 注文 DB とメッセージ基盤は、通常ひとつの DB トランザクションで更新できない
- 速報用の NoSQL を置く場合も、売上の正しさを確定する元データを決めておく
- BlobCreated は Blob の書き込み方法によって発火条件が異なる。書き込み完了を確認しても、CSV の内容が正しいとは限らない
