# 問題: 商品データの一括取込（中級）

## 背景

複数の仕入先が商品 CSV と画像を管理画面からアップロードする。CSV の列は仕入先ごとに少し異なり、色や素材など商品属性も増えていく。取込後、運用担当者はエラー行を確認し、利用者は商品一覧を閲覧する。

## 前提と要件

- 管理画面とアップロード API は Azure App Service で動かす
- 1 ファイルは最大 1 GB、最大 10 万行。画像の変換も必要で、処理は数分かかる
- 同じファイルが二重にアップロードされたり、イベントが重複して届いたりする可能性がある
- 価格・在庫は商品 ID に対して整合性が必要。商品説明・属性は仕入先ごとに形が異なる
- 利用者向け商品一覧には価格と商品説明を同時に表示し、ピーク時に毎秒 500 回参照される。取込結果の反映は数分遅れてよい
- 取込失敗時は原因と失敗行を確認し、修正後に再取込できること
- 候補として Blob Storage、Event Grid、Service Bus、Azure Functions、Container Apps Jobs、Azure SQL Database、Azure Cosmos DB を使える

## 設問

1. アップロードから取込完了、商品一覧への反映までの構成とデータの流れを示せ。ファイル原本、取込状態、商品データの置き場も明示せよ。
2. Blob Storage に新しいファイルが置かれたことを、どう処理基盤へ伝えるか。Event Grid から直接処理する案と、Service Bus を間に置く案を比較し、今回の要件で選べ。
3. 検証・画像変換・10 万行の取込に、Functions と Container Apps Jobs をどう使い分けるか。長い処理の分割単位と再実行方法を述べよ。
4. 価格・在庫、商品説明・属性、CSV と画像の原本、取込エラーを、それぞれ Azure SQL・Cosmos DB・Blob Storage のどこへ置くか。Cosmos DB を使う場合は、主な読み方に合う文書の単位とパーティションキー、価格を一覧へ反映する方法も提案せよ。
5. 同じファイルやイベントの重複によって、価格や在庫が意図せず二重更新されない方法を示せ。ファイルの識別子、取込バージョン、更新の条件をどう持つか。
6. 商品一覧への反映が遅れる間、管理画面にどの状態を表示するか。途中失敗した取込を再開・再実行するときに、利用者向けのデータをどう守るか。

## ヒント

- Event Grid が知らせるのは「何かが起きた」ことで、ファイル本体は Blob Storage にある
- 価格と在庫に必要な整合性、商品属性に必要な柔軟さは同じとは限らない
- SQL と Cosmos DB の両方に商品情報を持つなら、どちらを正本にするか決める
- イベント通知が2回届いても安全な取込単位を考える
