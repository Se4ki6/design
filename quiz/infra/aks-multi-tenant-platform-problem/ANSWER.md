# 回答:共有AKSプラットフォームの設計(AKS中級)

- 問題: `question\infra\aks-multi-tenant-platform-problem.md`

## 設問1: クラスタ構成

### 自分の回答

- クラスタは1で十分(サービスごとに異なるノードをもつ必要がある場合でも、ノードプールを分ければ対応可能)
- ノードプールをサービスで分ける
- User にアプリ・バッチを配置、System を共有する

### 模範解答

#### クラスタ数: 1つ

- 5チームは Namespace + RBAC + ResourceQuota で分離できるため、クラスタは1つで足りる
- クラスタを分けると、コントロールプレーン、アップグレード、監視、ネットワークなどの運用コストが増える。今回の「コスト極力抑えたい」「運用負荷が課題」という背景に合わない
- ただし、規制対応や強い分離(ノードやカーネルレベルの分離)が必要になった場合は、別クラスタを検討する

#### ノードプール構成

| プール | 種別 | 用途 | VM / 課金 | スケール |
|---|---|---|---|---|
| system | System | CoreDNS、metrics-server などのシステムPod専用 | 汎用小型VM | 最低3ノード(各ゾーン1) |
| api | User | Web API | 汎用VM | HPA + Cluster Autoscaler で伸縮 |
| batch | User | 夜間バッチ | CPU/メモリ大型VM、Spot VM | min=0。夜間のみスケールアウト |

- **System プールを分ける理由**
    - 業務Podの暴走やスケール・アップグレードが、DNS などクラスタ基盤に影響しないようにする
    - `CriticalAddonsOnly=true:NoSchedule` の taint を付け、業務Podを置かない
    - System プールはクラスタに1つで、全チームが共有する(チームごとには持たない)
- **User プールに業務Podを置く**
    - アプリ(Web API)とバッチは、別の User プールに配置する

#### 可用性ゾーン

- 各ノードプールを Zone 1 / 2 / 3 に分散させる
- System プールは各ゾーンに最低1ノードを置く(計3ノード以上)
- ゾーン障害時もサービスを継続できるようにする

#### ノードプールを分ける基準

- 基準は「チーム別」ではなく「**ワークロード特性別**」にする(チーム別にするとプールが増えすぎ、リソース効率が落ちる)
- 分ける観点は次のとおり
    - VM サイズ(バッチはCPU/メモリ大型)
    - スケール特性(APIは常時稼働で変動、バッチは夜間のみ)
    - コスト(バッチは Spot VM 可、APIは通常VM)
    - 障害・負荷の影響範囲(バッチがAPIのリソースを奪わない)
- 配置は taint / toleration と nodeSelector(または affinity)で制御する
    - 例: batch プールに `workload=batch:NoSchedule` を付け、バッチPodだけが toleration を持つ

### 自分の回答との差分

- 「クラスタは1」「ノードプールで分ける」は合っている
- 次の点を補うとよい
    - System プールの分離理由と taint
    - 可用性ゾーンの分散
    - ノードプールを分ける基準(特性別であり、サービス別・チーム別ではない)
    - クラスタ1とした根拠(分離の強さと運用コストのトレードオフ)
