# 回答:検索付き商品一覧のパフォーマンスと正しさ(React 中級)

- 問題: `question\front\react-search-list-problem.md`

※ 設問1のみ。設問2〜6は未回答。

---

# Part A. 私の回答(概要)

## 設問1

- `filtered` は依存配列がなく、毎レンダリングで再計算される
  - `products` と `query` から機械的に決まるので、メモ化できる
  - そもそも state にせず、必要な箇所で直接計算すれば十分
- `React.memo` が効かないのは、`toggleFavorite` が毎回別の参照として生成されるから
- `favorites` を ID で持っているので、API で新しい配列が返ると、お気に入りが指すアイテムが変わる

### 採点メモ(45 / 100点)

- ○ `React.memo` は参照比較であること、導出値を state にしない考え方
- △ `filtered` は state ではなく普通の `const`。二重フィルタ(サーバーとクライアントの両方で絞り込み)には触れられていない
- △ 参照が変わる原因は `toggleFavorite` だけではない。`onToggle={() => toggleFavorite(p.id)}` のインライン arrow が行ごとに毎回新規生成されることが直接の原因
- × ID で持つのは正しい設計(ID は再取得しても安定)。問題点ではない
- 抜け: 競合状態、Stale closure、`includes` の O(n)、エンコード/エラー処理、デバウンスなし、state の置き場所、全件描画

# Part B. 模範解答(設問1)

## 問題点と原因

| # | 問題 | 原因 |
|---|---|---|
| 1 | 古いレスポンスで上書きされる(競合状態) | `useEffect` にクリーンアップがない。リクエストの完了順は送信順と一致せず、遅れて返った古い結果が `setProducts` で新しい結果を上書きする |
| 2 | 二重フィルタ | サーバーに `q=${query}` を渡しているのに、クライアントでも `p.name.includes(query)` で絞っている。処理が重複し、一致判定のルール(大文字小文字、部分一致の仕様)が食い違うと結果がずれる |
| 3 | `filtered` を毎回計算 | レンダリングのたびに 5,000 件を走査する。`products` と `query` から決まる導出値なので、不要な計算であり、必要なら `useMemo`。#2 を解消すれば不要 |
| 4 | `React.memo` が効かない | `onToggle={() => toggleFavorite(p.id)}` が行ごとに毎回新しい関数になり、props の参照が変わる。`toggleFavorite` 自体も毎回再生成される |
| 5 | Stale closure | `toggleFavorite` が、レンダー時点の `favorites` を直接参照している。連続クリックや非同期処理で更新が失われる |
| 6 | お気に入り判定が遅い | `favorites.includes(p.id)` は O(n)。全行で呼ぶと O(行数 × お気に入り数) |
| 7 | リクエストの作り方 | `query` を `encodeURIComponent` していない。`res.ok` の確認やエラー処理がない。キー入力のたびにリクエストを送っている(デバウンスなし) |
| 8 | 検索条件が戻るとリセット | `query` / `category` がローカル state なので、アンマウントで消える |
| 9 | 全件描画 | 5,000 行を DOM に出している |

補足:

- `favorites` を **ID の集合で持つのは正しい**。ID は再取得しても変わらないので、一覧が入れ替わってもお気に入りは保たれる。アイテム本体を持つ方が、再取得で古いオブジェクトが残る問題を起こす
- #2 は設計判断が必要。商品が 5,000 件でクライアントに全部あるなら、クライアント絞り込みだけにしてサーバー検索を外す。件数が多い、または権限や集計が絡むなら、サーバー絞り込みだけにしてクライアント側のフィルタを消す
