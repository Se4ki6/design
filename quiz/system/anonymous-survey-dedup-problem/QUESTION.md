# 問題:ログインなしアンケートサイトの重複回答排除(中級〜上級)

- 回答: `ANSWER.md`

## 背景

ある消費財メーカーのマーケティング部門が、自社でアンケート配信基盤を運用している。
年間 300 本ほどのアンケートを作成し、常時 10〜20 本が同時に公開されている。回答者に**ログインやアカウント登録は求めない**(回答率が大きく下がるため)。

配布経路は2種類ある。

- **オープン配布**: SNS 投稿・Web 広告・店頭 POP の QR コードから、全員共通の URL でアクセスする
- **個別配布**: 会員メールリストに、1人1つの**個別 URL**(推測困難なトークン付き)を送る

多くのアンケートには**抽選でギフト券が当たる**特典が付いており、過去に以下の問題が起きた。

- 同一人物がブラウザを変えて数十回応募し、当選者に同一人物が複数含まれていた
- スクリプトによる大量の自動送信で、集計結果が大きく歪んだ
- 逆に、大学の学内 Wi-Fi やモバイル回線から回答した正規の回答者が「回答済みです」と表示され、回答できなかった
- 「送信」ボタンの連打や通信リトライで、同じ回答が2件登録されていた

### 想定している基本構成(前提として使ってよい)

- 入口: Azure Front Door(WAF 付き)
- アプリ: Azure App Service 上の Web アプリ(回答画面・管理画面・API)
- DB: Azure SQL Database(アンケート定義・回答・集計はすべて RDB で管理)
- 必要に応じてキャッシュ・キュー・バッチ実行基盤などを追加してよい

## 要件

### 規模

- 平常時は 1 分あたり数十件の回答。キャンペーン開始直後や TV 露出時は**ピーク 3,000 件/分**
- 1 アンケートあたりの回答数は数百〜30 万件
- アンケートは最大 5 ページ・50 問。途中で離脱し、**同じブラウザなら後から再開できる**

### 重複排除

- 原則「**1 人 1 アンケート 1 回答**」とする。ただしログインがない以上、完全な同一人物判定は不可能であることを前提に、**どこまでを確実に防ぎ、どこからを確率的に扱うか**を設計で明示すること
- 個別配布の URL は、**同じトークンでの回答完了は必ず 1 回まで**(同時に送信されても 2 件にならない)
- 送信の二重実行(連打・リトライ・複数タブ)で回答が重複登録されないこと
- 共有 IP(学内・社内 NAT、モバイルの CGNAT)の正規回答者を**一律にブロックしない**こと
- 自動送信(ボット)を抑止すること
- 抽選前に、運営担当者が「疑わしい回答」を確認・除外できること。集計画面では「全件」「疑わしい回答を除いた件数」を切り替えて見られること

### プライバシー・運用

- 回答は匿名扱い。氏名・メールアドレスは、当選者が賞品送付のために任意で入力する場合のみ別管理で保持する
- IP アドレスや端末情報を**生のまま長期保存しない**(社内ポリシー: 判定目的での保持はアンケート終了後 30 日まで)
- 公開中のアンケートでも、誤字修正などの軽微な設問変更が行われることがある

## 設問

1. **重複のパターン分類と方針**
   想定される重複・不正のパターンを列挙し、それぞれを「同期的に拒否する(ハード)」「受け付けるがフラグを付ける(ソフト)」「許容する」のどれで扱うか、理由とともに整理せよ。オープン配布と個別配布で方針はどう変わるか

2. **識別シグナルの設計**
   ログインなしで回答者を識別・推定するために使えるシグナル(例: ブラウザに保存する識別子、個別トークン、IP、端末特徴、ボット判定の結果など)を挙げ、それぞれの**強さ・回避のしやすさ・誤検知のリスク**を比較せよ。ブラウザ側に識別子を保存する場合、どこに・どんな値を・どの寿命で保存するか(ブラウザのトラッキング防止機能やシークレットモードの影響も考慮すること)

3. **RDB のデータモデルと一意性の保証**
   回答セッション・回答・識別シグナル・個別トークンなどのテーブル構成と、主要な**一意制約・状態遷移**を示せ。特に次の2点を、アプリ側のチェックだけに頼らず RDB でどう保証するか説明せよ
   - 同一個別トークンでの同時送信が来ても、完了回答が 1 件になること
   - 送信の二重実行が 1 件の回答として扱われること(冪等性)

4. **回答のデータフロー**
   「アンケート URL にアクセス → 回答開始 → ページごとの途中保存 → 最終送信 → 完了画面」までの流れを、どのタイミングで何を発行・検証・保存するかを中心に示せ。途中保存中の回答は重複判定の対象にするか

5. **ボット・大量送信への対策と Azure サービスの選定**
   レート制限・ボット判定をどの層で行うか設計せよ。以下の観点で、採用する Azure サービスと**代替候補との違い・採用理由**を説明すること
   - エッジでのレート制限・WAF(例: Front Door の WAF と Application Gateway の WAF の違い、どちらに置くか)
   - 短期カウンタや同時実行制御の置き場所(RDB で行う場合と、Azure Cache for Redis 等のインメモリストアを使う場合の違い)
   - 人間であることの確認手段(CAPTCHA 系の外部サービスを使う場合、Azure 側でどう連携し、いつ要求するか)

6. **非同期の重複スコアリングと抽選前クレンジング**
   送信時には判定しきれない「同一人物らしさ」(同じハッシュ化 IP + 似た端末特徴から短時間に複数回答、回答内容がほぼ同一、回答時間が極端に短い など)を、送信後に非同期で評価する仕組みを設計せよ。
   - 送信処理と判定処理をどう疎結合にするか(採用するキュー・実行基盤と、代替候補との違い。例: Service Bus / Storage Queue / Event Grid、Functions / WebJobs / Container Apps Jobs など)
   - 判定結果を RDB のどこに持ち、集計画面の「全件 / 疑わしい回答除外」をどう実現するか
   - 判定ルールを後から変更したとき、既存回答の再判定をどう行うか

7. **プライバシーとデータ保持**
   IP や端末情報をハッシュ化して保持する場合、単純なハッシュでは何が問題か。ソルト(ペッパー)の管理場所と範囲(アンケートごと/期間ごと)、30 日後の削除方法、鍵・シークレット管理に使う Azure サービスと代替手段との違いを述べよ

8. **エッジケース**
   次のケースでシステムがどう振る舞うべきか、それぞれ説明せよ
   - a. 家族で 1 台のタブレットを共有しており、2 人が別々に回答したい
   - b. 個別 URL が SNS に転載され、本人以外が先に回答してしまった
   - c. 回答の途中でアンケートの締切時刻を過ぎた(最終送信が締切後に届いた)
   - d. 最終送信の DB 書き込みは成功したが、レスポンスがクライアントに届かず、ユーザーが再送信した
   - e. 公開中に設問の文言修正・選択肢の追加が行われ、旧バージョンで途中保存していた回答者が再開した
   - f. 同じ大学キャンパスの IP から、授業中の 10 分間に 200 件の回答が届いた
   - g. 判定用 Redis(を使う場合)が一時的にダウンした。送信を止めるか、通すか

## ヒント

- 「重複を防ぐ」と「正規回答者を弾かない」は**トレードオフ**。偽陽性と偽陰性、どちらのコストが高いかはアンケートの目的(特典の有無、統計の精度)で変わる
- ブラウザに保存した識別子は、本人が消せば消える。**「確実に防げる」のはどのシグナルだけか**
- RDB の一意制約は「同時に来た 2 つの INSERT」に対して何を保証するか。チェックしてから INSERT する方式の何が危ないか
- 冪等キーは誰が・いつ発行するか。サーバーが回答開始時に発行するセッション ID は使えないか
- 送信時にすべてを判定しようとすると、ピーク時のレイテンシとロック競合はどうなるか
- 「拒否」ではなく「フラグ」にしておけば、ルールを後から変えても回答データは失われない
- アンケート ID を含めてハッシュ化すると、別アンケート間での突き合わせはできるか(それは望ましいか)
