# シグナリングとメディア

問題: [QUESTION.md](../QUESTION.md)(設問1の参考)

## 用語

| 用語 | 意味 |
|---|---|
| シグナリング(Signaling) | 通話の**制御情報**のやりとり。発信・着信・応答・拒否・切断、相手の居場所、使えるコーデックやアドレスの交換など |
| メディア(Media) | 通話の**中身**。音声(ビデオ)をエンコードしたデータ |
| コントロールプレーン / データプレーン | ネットワーク一般の呼び方。シグナリング ≒ コントロールプレーン、メディア ≒ データプレーン |
| セッション | 1回の通話。シグナリングで「確立 → 変更 → 終了」が管理される |

## 2つの通信の性質の違い

| 観点 | シグナリング | メディア |
|---|---|---|
| データ量 | 小さい(1通話で数KB〜数十KB程度のメッセージが数回〜数十回) | 大きく連続的(音声で数十kbps が通話中ずっと流れる) |
| 頻度 | イベント発生時のみ(発信、応答、切断など) | 20ms ごとなど、一定間隔で途切れなく |
| 重視すること | **確実に・順序通り**届くこと(「応答」が消えると通話が始まらない) | **遅延が小さい**こと(古いデータは届いても役に立たない) |
| 欠損への耐性 | 低い(欠けたら再送が必要) | 比較的高い(少し欠けても聞き取れる・補間できる) |
| 通信相手 | クライアント ⇔ サーバー(相手の場所はサーバーが知っている) | 理想は**端末 ⇔ 端末(P2P)**。無理ならリレーサーバー経由 |
| サーバー負荷の特徴 | 接続数(常時接続)・イベント処理 | 帯域・パケット転送量 |
| スケールのさせ方 | ステートフルな接続管理・ユーザーの在席(Presence)管理 | 帯域の確保、リージョン分散、P2Pでサーバーを通さない |

## 一般的なアーキテクチャ

```
          シグナリング(TCP系: WebSocket / HTTPS / SIP over TLS など)
  ┌──────────┐      ┌──────────────────┐      ┌──────────┐
  │ Client A │ ───▶ │ シグナリングサーバー │ ◀─── │ Client B │
  └──────────┘      └──────────────────┘      └──────────┘
        │                     │ (相手がオフライン/バックグラウンド)
        │                     ▼
        │             プッシュ通知 (APNs / FCM)
        │
        │   メディア(UDP系: RTP / SRTP)
        └──────────────────────────────────────▶ Client B
               直接(P2P) or リレーサーバー経由
```

- シグナリングサーバーは「誰が今どこにいるか」「この通話の状態は何か」を管理する
- メディアはシグナリングで交換した情報(アドレス・コーデック)をもとに、別経路で流れる
- この分離は SIP/VoIP、WebRTC、携帯電話網(IMS / VoLTE)など、ほぼすべての通話システムで共通の考え方

## シグナリングで使われるプロトコル・経路

| 方式 | 概要 | 主な用途 |
|---|---|---|
| **WebSocket**(over TLS) | クライアント⇔サーバーの常時双方向接続。サーバーから即時に着信を押し込める | アプリ起動中の端末へのリアルタイム通知。WebRTCアプリの定番 |
| HTTPS(REST) | リクエスト/レスポンス型 | 発信要求・通話履歴など、クライアント起点の操作 |
| MQTT / XMPP | メッセージング向けプロトコル。常時接続で軽量 | チャットアプリのメッセージ基盤と共用するケース |
| gRPC(双方向ストリーミング) | HTTP/2上のストリーム | 自社サービス間、モバイルクライアント |
| **SIP**(Session Initiation Protocol, RFC 3261) | 電話の標準シグナリング。INVITE / 180 Ringing / 200 OK / ACK / BYE などのメソッド | VoIP、IP電話、携帯網(VoLTE)。UDP/TCP/TLS上で動く |
| **プッシュ通知**(APNs / FCM) | OSベンダーのサーバー経由で端末を起こす | **アプリが閉じている・バックグラウンドの相手**への着信通知 |

### プッシュ通知の補足

- アプリが終了・スリープ中だとWebSocketは切れているため、サーバーから直接は届かない
- iOS: **VoIP Push(PushKit)** + **CallKit** で、OS標準の着信画面を表示できる(VoIP Pushを受けたら必ずCallKitで着信を報告する必要がある)
- Android: **FCM の高優先度メッセージ** + `ConnectionService` / フルスクリーン通知で着信画面を表示
- プッシュは「起こす合図」として使い、起動後にWebSocket等で詳細なシグナリングを続けるのが一般的

### SDP(Session Description Protocol, RFC 8866)

- シグナリングで運ばれる「**メディアの設定情報**」の書式
- 中身の例: 使えるコーデック(Opus など)、メディアのIP/ポート、暗号化の鍵情報(指紋)、ICE候補
- **Offer / Answer モデル**: 発信側が Offer(こういう条件で通話したい)を送り、着信側が Answer(この条件でOK)を返す
- SIPでもWebRTCでも、このSDPのやりとりが通話確立の中心

```
v=0
o=- 4611731400430051336 2 IN IP4 127.0.0.1
m=audio 9 UDP/TLS/RTP/SAVPF 111
a=rtpmap:111 opus/48000/2
a=candidate:1 1 udp 2122260223 192.168.0.10 54321 typ host
a=fingerprint:sha-256 AB:CD:...
```

## メディアで使われるプロトコル・経路

| プロトコル | 層 | 概要 |
|---|---|---|
| **UDP** | トランスポート | 再送・順序制御なし。遅延が小さい。メディアのほぼ標準 |
| **RTP**(Real-time Transport Protocol, RFC 3550) | アプリ(UDP上) | 音声パケットに**シーケンス番号・タイムスタンプ**・ペイロード種別を付ける。受信側での並べ替え・欠損検出・再生タイミング計算に使う |
| **RTCP**(RTP Control Protocol) | アプリ(UDP上) | 通信品質の統計(パケットロス率、ジッター、往復遅延)を定期的に交換する |
| **SRTP**(Secure RTP, RFC 3711) | アプリ | RTPの暗号化・改ざん検知版。WebRTCでは必須 |
| **DTLS**(Datagram TLS) | UDP上 | UDP版TLS。WebRTCではSRTPの鍵交換に使う(DTLS-SRTP) |
| **ICE / STUN / TURN** | 経路確立 | NAT越えのための仕組み(設問3の範囲) |

### 音声コーデック

| コーデック | 特徴 |
|---|---|
| **Opus**(RFC 6716) | WebRTCの必須コーデック。6〜510kbps可変、音声通話なら16〜32kbps程度。パケットロス耐性機能(FEC)あり。20msフレームが一般的 |
| G.711(PCMU/PCMA) | 古典的な電話品質。64kbps固定。電話網との接続で使われる |
| AMR-WB / EVS | 携帯網(VoLTE)向け |

- 目安: Opus 20msフレーム → 1秒に50パケット。1通話(片方向)で数十kbps(RTP/UDP/IPヘッダ込み)

### メディアの経路パターン

| パターン | 概要 | 特徴 |
|---|---|---|
| **P2P(直接)** | 端末同士が直接UDPで送り合う | 遅延最小、サーバー帯域コストなし。NATで不可な場合がある |
| **リレー(TURN)** | リレーサーバーがパケットを中継するだけ | P2Pできないときのフォールバック。帯域コストがかかる |
| SFU(Selective Forwarding Unit) | サーバーが受け取って必要な相手に転送 | 主にグループ通話向け |
| MCU(Multipoint Control Unit) | サーバーがミキシングして配信 | グループ通話向け。サーバー負荷大 |

## WebRTC が担うもの / 担わないもの

| 範囲 | WebRTC の扱い |
|---|---|
| メディアの取得・エンコード(Opus) | 担う |
| RTP/SRTP での送受信、DTLS鍵交換 | 担う |
| ICE(STUN/TURNを使った経路探索) | 担う(ただし**STUN/TURNサーバー自体は自前 or 外部サービスで用意**) |
| ジッターバッファ、パケットロス補償、エコーキャンセル | 担う |
| SDP の生成(`createOffer` / `createAnswer`) | 担う |
| **シグナリング(SDP・ICE候補を相手に届ける手段)** | **担わない**。WebSocket等で自前実装する(仕様上あえて定めていない) |
| ユーザー認証、在席管理、着信通知(プッシュ) | 担わない |

## 実サービスの例(公開情報ベース)

| サービス | シグナリング | メディア |
|---|---|---|
| 一般的なWebRTCアプリ | WebSocket + 独自JSONメッセージ | SRTP over UDP(P2P、ダメならTURN) |
| IP電話 / VoLTE | SIP | RTP/SRTP over UDP |
| WhatsApp(公開記事より) | 既存のメッセージング接続(XMPP派生)上で通話制御 | SRTP、P2P優先・リレーへフォールバック |
| Zoom / Teams(会議) | 独自プロトコル / SIP等 | UDP優先、ダメならTCP/TLS(443)へフォールバック |

> 注: 実サービスの内部構成は公開情報の範囲。詳細は各社の技術ブログ等で確認すること。
