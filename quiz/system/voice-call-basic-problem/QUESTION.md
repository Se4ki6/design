# 問題:1対1音声通話サービスの設計(初級)

- 回答: `answer\system\voice-call-basic-problem.md`

## 背景

スマホ向けのメッセージアプリに、**友だち同士で1対1の音声通話**ができる機能を追加したい。
(LINE通話 や WhatsApp 通話 のようなイメージ。ビデオ・グループ通話は今回は対象外)

## 要件

- 利用者は 100 万人、同時通話数はピーク時 1 万件
- 相手に「着信」を知らせ、相手が応答したら通話が始まる
- 会話の遅延(口から耳まで)は **300ms 以下**が目標
- 多くの利用者は自宅Wi-Fiやモバイル回線にいる(= **NAT の内側**にいる)
- 通話中に多少音が途切れても、通話自体が切れないこと

## 設問

1. 通話の「**シグナリング**(発信・着信・応答・切断のやりとり)」と「**メディア**(音声データそのもの)」はなぜ分けて考えるのか。それぞれどんな経路・プロトコルで流すのが適切か答えよ
2. 音声データの転送に **TCP ではなく UDP** がよく使われる理由を説明せよ
3. 両者がNATの内側にいると、直接通信できないことがある。**STUN** と **TURN** はそれぞれ何をするものか、どんな順で使うかを説明せよ
4. 発信してから相手の端末が鳴るまでの流れを、登場するコンポーネント(クライアントA/B、シグナリングサーバー、プッシュ通知など)を使って箇条書き or 簡単な図で示せ
5. 音声データが一部届かなかったり、順番が前後したりした場合、受信側では何をすればよいか(キーワードを1つ以上挙げて説明)

## ヒント

- 「遅れて届いた正確なデータ」と「多少欠けた今のデータ」、通話ではどちらが嬉しいか
- アプリが閉じている相手に着信を届けるには?
- WebRTC がこの問題のかなりの部分を担ってくれる(何を担い、何を自前で用意する必要があるか)
- 受信バッファ(ジッターバッファ)
