# 01. 要件定義(ドラフト)

> AI が叩き台として作成。末尾の「要検討の論点」を決めて確定させる。

## 想定する利用シーン

- 購入者がカートから注文を確定すると、決済・在庫引当・出荷指示が自動で進む
- 途中で失敗(決済エラー、在庫切れ)した場合は、注文を取り消し、確保済みのリソースを戻す
- 年に数回の大型セールで、通常の数十倍の注文が短時間に集中する

## 機能要件

### 必須

1. **注文受付**: 注文を受け付け、注文 ID を即座に返す(処理は非同期で進む)
2. **決済**: 外部決済代行サービスでオーソリ(与信確保)し、出荷時に売上確定する
3. **在庫引当**: 注文商品の在庫を確保する。在庫不足なら注文を失敗させる
4. **出荷指示**: 決済・在庫が揃ったら倉庫システムへ出荷を依頼する
5. **補償処理**: いずれかのステップが失敗したら、完了済みステップを取り消す(与信取消、在庫戻し)
6. **注文状態の参照**: 購入者が注文の状態(受付中 / 確定 / 出荷済み / 失敗 など)を確認できる
7. **キャンセル**: 出荷前であれば購入者が注文をキャンセルできる
8. **通知**: 注文確定・出荷・失敗をメールで通知する
9. **二重注文の防止**: ボタン連打や通信リトライで同じ注文が重複して作られない

### あれば良い

- ポイント・クーポンの適用(Saga の参加者が増えるケースとして)
- 返品・返金フロー
- 注文イベントを分析基盤へ流す

## 非機能要件(仮置き)

| 項目 | 目標値(仮) | 前提・根拠 |
|---|---|---|
| 注文数(平常時) | 100 万件/日 | 中〜大規模 EC を想定 |
| 注文数(セール時ピーク) | 平常時平均の 50 倍の QPS が数十分続く | タイムセール開始直後に集中 |
| 注文受付 API の応答時間 | p99 500ms 以内 | 受付のみ。後続処理は非同期 |
| 注文確定までの時間 | 平常時 p95 30 秒以内 | 決済・在庫引当を含む |
| 在庫の整合性 | 過剰販売(在庫以上の受注)を起こさない | 要検討(許容する場合の補填方針) |
| 注文データの耐久性 | 受付成功を返した注文は失わない | |
| 可用性 | 注文受付 99.95% | 売上に直結するため |
| 外部依存 | 決済代行の障害・遅延時も注文受付は止めない | 要検討 |
| 監査 | 注文状態の遷移履歴をすべて残す | 問い合わせ対応・会計監査のため |

## 要検討の論点

1. Saga はオーケストレーション(中央の調整役)とコレオグラフィ(イベントの連鎖)のどちらにするか
2. 在庫引当のタイミング(カート投入時 / 注文確定時 / 決済後)と、セール時のホット在庫の扱い
3. DB 更新とイベント発行の整合性をどう保つか(Outbox / Change Feed / 2PC を避ける理由)
4. 各サービスの冪等性をどう実現するか(冪等キー、処理済みメッセージの記録)
5. メッセージ基盤の選定(コマンドとイベントで使い分けるか、順序保証にセッションを使うか)
6. 決済代行がタイムアウトした場合(成功したか不明な場合)の扱い
