# 01. 要件定義(ドラフト)

> AI が叩き台として作成。末尾の「要検討の論点」を決めて確定させる。

## 想定する利用シーン

- 企業(ワークスペース)単位で利用し、チャンネルや DM で会話する
- PC ブラウザとスマホアプリの両方から同時に接続する

## 機能要件

### 必須

1. **メッセージ送受信**: チャンネル / DM / グループ DM にテキストを送信し、参加者にリアルタイム配信する
2. **チャンネル管理**: 公開・非公開チャンネルの作成、参加・退出
3. **履歴取得**: 過去メッセージを遡って読み込める(ページング)
4. **スレッド返信**: メッセージに対してスレッドで返信できる
5. **既読・未読**: チャンネルごとの未読数、どこまで読んだかを複数端末で同期する
6. **プレゼンス**: オンライン / 離席状態、入力中表示
7. **オフライン同期**: 再接続時に、切断中のメッセージを取りこぼしなく取得する
8. **プッシュ通知**: アプリを閉じている端末にメンション・DM を通知する
9. **ファイル添付**: 画像・ファイルを添付できる
10. **編集・削除**: 自分のメッセージを編集・削除できる

### あれば良い

- メッセージ全文検索
- リアクション(絵文字)
- メッセージ配信のサーバー側 Webhook(Bot 連携)

## 非機能要件(仮置き)

| 項目 | 目標値(仮) | 前提・根拠 |
|---|---|---|
| ユーザー数 | 登録 1,000 万人、DAU 300 万人 | 中規模の SaaS を想定 |
| 同時接続数 | ピーク 150 万接続 | DAU の 50%、複数端末を考慮 |
| 送信メッセージ数 | 1 人 1 日 40 通 → 1.2 億通/日 | ピークは平均の数倍 |
| 最大チャンネル人数 | 10 万人 | 全社告知チャンネルを想定。ファンアウト設計に影響 |
| 配信遅延 | 同一リージョン内 p99 500ms 以内 | 送信から受信者の画面表示まで |
| 順序 | チャンネル内で全員に同じ順序で見える | 要検討(厳密さの程度) |
| 耐久性 | 送信成功を返したメッセージは失わない | |
| 可用性 | 99.95% | 業務インフラとして利用されるため |
| 履歴保持 | 無期限(ワークスペース設定で短縮可) | ストレージ見積もりに影響 |

## 要検討の論点

1. 順序保証の単位と方式(チャンネル単位の連番 / タイムスタンプ / サーバー側でのシーケンス採番)
2. 大規模チャンネル(10 万人)へのファンアウトを書き込み時に行うか、読み込み時に行うか
3. 配信保証のレベル(at-least-once + クライアント側重複排除 で良いか)
4. マルチリージョン時、ワークスペースを特定リージョンに固定するか、複数リージョンから書き込むか
5. プレゼンスの更新頻度と、その書き込み負荷をどこまで許容するか
6. 接続管理をマネージド(Web PubSub)に任せるか、自前の WebSocket サーバーを持つか
