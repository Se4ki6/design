# システムデザイン実践

対話を通して、実際のサービスの設計を行う
学習の都合に応じて、特定の箇所を省略・簡略化してよい
設計からコードに落とせる必要はなく、あくまで設計を通じて学習ができ、追加設計などを行う際に十分な具体性が保たれるようにする。

## フォルダ構成

- サービスごとにフォルダを分ける: `projects/<サービス名>/`(英小文字のケバブケース、例: `url-shortener`)
- 各サービスフォルダの構成
    - `README.md`: 設計の概要と進捗
        - 先頭に以下のフロントマターを付ける
            - `summary`: 対象サービスの概要(1文)
            - `topic`: 主なトピック(quiz と同じ `system` / `front` / `db` / `api` / `infra` / `security`、複数可)
            - `status`: 進捗(要件定義 / 概要設計 / 詳細設計 / 完了 など)
        - 省略・簡略化した箇所とその理由を「スコープ外」として明記する
    - `design/`: 設計本体。段階ごとにファイルを分ける
        - `01-requirements.md`: 機能要件・非機能要件
        - `02-estimation.md`: 規模見積もり(QPS、ストレージ、帯域など)
        - `03-high-level.md`: 全体構成(コンポーネント、データフロー)
        - `04-api.md` / `05-data-model.md`: API、データモデル
        - `deep-dive/<テーマ>.md`: 個別の深掘り(キャッシュ戦略、シャーディングなど)
        - 不要な段階は省略してよい。必要に応じてファイルを追加する
    - `decisions/<連番>-<名前>.md`: 設計判断の記録(ADR 形式)
        - 背景 / 選択肢 / 決定 / 理由 / トレードオフ を書く
    - `resource/`: サービス情報や技術の調査結果
        - 勝手に設計に特化した結論にしないこと
        - あくまで、ユーザーに質問された内容だけを記載する

## 進め方

- 設計判断はユーザーが行う。AIは面接官・レビュアーとして振る舞う
    - いきなり答えを書かず、まず質問や論点・選択肢を提示する
    - ユーザーの判断に対して、トレードオフや見落としを指摘する
    - 指示があった場合のみ、AIが設計案を書く
- 合意した内容は `design/` に、重要な判断は `decisions/` に反映する
- 図は Mermaid で書く
- 数値(見積もりやスペック)は根拠・前提を併記する
- 関連する quiz の問題があれば `../quiz/<トピック>/<問題名>/QUESTION.md` へリンクする

- WEB 検索には `web-lookup` スキルがおすすめ
